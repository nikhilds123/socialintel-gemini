Why AgenticOrg didn't fit Plug

Plug is an agent-driven marketing tool built to get you your first 1,000 users. We tried to hand its first step to AgenticOrg's agents. This is what happened.

24 October 2026

What we tried

We wanted AgenticOrg to do step one of Plug: read the product link and build the product profile that the rest of the plan depends on. Over one day we checked their API, SDK, MCP server and docs, wired a test route into the app, wrote a terminal probe, and created a custom agent in their dashboard.

The route never completed a single run.

What blocked it

  1. Their API blocks browser calls. Plug is a single web page. AgenticOrg's API refuses every browser origin; the preflight check returns "Disallowed CORS origin", even for their own app domain. The page cannot call AgenticOrg directly.
  2. Their hosted MCP endpoint is for shopping, not agents. The only hosted MCP endpoint, /mcp, uses permission scopes like buyer_agent and payment. It cannot run a marketing agent, so it cannot be attached as a connector.
  3. The one working path is desktop-only. The remaining route is their local MCP server running inside the Claude desktop app. It works only for the page owner, on that one machine. Real users on the web would never reach it.
  4. No agent reads a website. All 55 built-in agents are finance, HR, operations or SEO-metrics tools. We would still fetch the page ourselves and send the text along, so AgenticOrg adds a hop without adding ability.
  5. The API key never validated. The key returned "Invalid API key" on all three hosts. The hosts are separate deployments with different agent catalogues, and it is unclear which one the dashboard key belongs to.
  6. The custom agent cannot call its model. We built a "Marketing Intake Analyst" agent with a clean JSON prompt. Every run failed with OpenAIInvalidRequestError: agent execution failed. The workspace's only model ID is one OpenAI does not serve. Fixing it needs the workspace admin.
  7. Governance built for back office, not a one-minute intake. Agents start in shadow mode and must be promoted. A confidence floor, 88% by default, sends runs to human approval instead of returning output. Default write tools such as schedule_social_post got attached without asking. Every run needs a company ID.
  8. Output shape is not guaranteed. Agents return free-form JSON. We would still need a Claude pass to fit it into the profile format, so the Claude call we were trying to replace stays.

What we built and kept

Everything stays in the code, switched off by default. The normal Claude path is untouched.

  • A Labs switch on the intake screen that sends the profile step to an AgenticOrg agent, and falls back to Claude on any failure.
  • A terminal script that runs an agent and reports whether its output is usable.
  • Setup notes with the API facts and the agent prompt we used.
  • The custom intake agent in our AgenticOrg workspace, still in shadow mode.

What would unblock it

All four are needed, and three of them sit with AgenticOrg or the workspace admin.

  • AgenticOrg allows our site's origin, or we run a small server that holds the key and forwards calls.
  • A valid API key issued on the same host as the dashboard.
  • The workspace's model setting points at a real model, or a Gemini key is added.
  • The custom agent promoted to active, with the confidence floor off and no default tools.

Decision

Plug keeps Claude and Firecrawl for the product analysis. It already works, runs in the browser for every user, and returns the profile in about a minute. AgenticOrg stays a Labs experiment we can switch on if the four items above get resolved.
